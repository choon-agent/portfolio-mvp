## 0. 세 줄 요약

- S&P 500을 대상으로 **스크리닝 → LLM Bull/Bear 리서치 → LLM 시나리오 → 최적화 → 리밸런싱** 5단계를 AWS Step Functions 체인으로 묶어 매주 월요일 자동 실행했다. 12주 유효 운영 동안 정기 실행 성공률 93%, LLM 호출 840건 재시도 0, 비용은 주 $1.
- 핵심 설계 원칙은 **"LLM은 판단 재료만, 가격과 매매는 결정적 코드"**였다. 이 분리 덕분에 LLM의 기여를 격리해서 측정할 수 있었다.
- 측정 결과: LLM이 내놓은 시나리오 확률은 **12주 내내 0.25/0.28/0.30 격자에 고정된 상수**였고(Brier 0.636, 무작위 0.667), 모델을 바꿔도 프롬프트를 고쳐도 안 바뀌었다. 파이프라인은 합격, 전제는 불합격. 그래서 v2는 LLM을 확률 입력에서 떼어내는 쪽으로 간다.

## 1. 왜 만들었나

[TODO: 개인 동기 1~2문단 — LLM 오케스트레이션을 실제 운영 환경에서 배우고 싶었다는 것, 수익이 목적이 아니었다는 것.]

프로젝트 시작 전에 **헌장(CHARTER)** 을 먼저 썼다. 목적 우선순위를 "LLM 학습 > 포트폴리오 산출물 > 퀀트 리서치 > 실제 돈"으로 고정하고, 충돌하면 상위가 이긴다고 못 박았다. 이 한 줄이 6개월 동안 가장 많이 참조된 문장이었다. "이 최적화가 수익률은 올리는데 의사결정이 블랙박스가 된다"는 제안이 나올 때마다 2순위(명료한 의사결정 로그)가 거부했다.

제약도 숫자로 박았다. 월 LLM 비용 $200 상한, 주 1회 리밸런싱, 포지션 최대 15개, 섹터 35%, 공매도·레버리지 금지, 페이퍼 $10,000. 그리고 **성공 기준에 수익률을 넣지 않았다.** 6개월은 실력과 운을 가를 표본이 아니라서다.

## 2. 전체 구조 — 5단계, LLM은 두 곳에만

```
[1] 스크리닝 (코드)       S&P 500 → 모멘텀·밸류 z-score → 20종목
       ↓
[2] Bull/Bear (LLM ×2)    종목당 강세·약세 분석가 각 1회 호출
       ↓
[3] 시나리오 (LLM ×1)     bull/base/bear 확률 + 근거 + 무효화 트리거
       ↓  가격은 LLM이 아니라 결정적 산식이 계산
[4] 최적화 (코드)         Mean-Variance + 제약 + 현금 규칙 → 목표 비중
       ↓
[5] 리밸런싱 (코드)       목표 비중 vs 보유 → 매매 → 페이퍼 계좌 2개
```

LLM은 2·3단계에만 있다. 1·4·5단계는 순수 코드다. 이건 비용 때문이기도 하지만 더 큰 이유는 **귀속(attribution)** 이다. 성과가 나빠졌을 때 "LLM 탓인지 산식 탓인지"를 분리해서 답할 수 있어야 학습이 된다. 결과적으로 이 분리가 12주 뒤 "LLM 탓이 아니라 산식 탓"이라는 진단을 가능하게 했다.

### 인프라

- **오케스트레이션**: Step Functions 상태 머신 1개. `RunScreening → BullBearMap → ScenarioMap → RunOptimizer → RunRebalancer`. Map 상태로 종목별 병렬(동시성 1~2 — Anthropic 분당 토큰 한도 때문).
- **실행 단위**: Lambda 7개. 1~3단계는 zip, 4·5단계는 **컨테이너 이미지**(numpy/scipy/cvxpy가 zip 50MB를 넘어서). zip은 GitHub Actions가 자동 배포, 컨테이너는 로컬 스크립트.
- **저장소**: S3 버킷 하나, 전부 `prefix/dt=YYYY-MM-DD/symbol=X.json` 파티션. 주간 실행마다 입력·중간 산출물·최종 비중·계좌 스냅샷이 전부 남는다. 이게 뒤에 나올 백테스트의 재료가 됐다.
- **스케줄**: EventBridge, 월요일 06:00 ET.

Athena를 쿼리 레이어로 계획했지만 6개월간 한 번도 안 썼다. 로컬 파이썬 스크립트가 S3를 직접 읽는 게 매번 더 빨랐다. 헌장 v0.3에서 제거.

## 3. 2단계 — Bull/Bear 에이전트: 같은 데이터, 반대 입장

종목 하나에 **같은 컨텍스트**(섹터, 피어 멀티플, 가격 요약, 분기 재무)를 주고 시스템 프롬프트만 다른 두 에이전트를 호출한다. 하나는 강세 논리만, 하나는 약세 논리만 쓴다. 출력은 Pydantic 스키마로 강제: `summary`(200자), `arguments[3..5]`(claim·evidence·confidence), `key_risks_to_thesis[1..3]`.

프롬프트에서 가장 공들인 건 **"하지 말 것"** 쪽이었다.

- 매수/매도/목표가 금지 — 매매는 룰이 한다.
- **스크리닝 신호(z-score)를 근거로 재사용 금지** — "왜 뽑혔는지"는 맥락이지 증거가 아니다.
- 리스크는 자기 논지를 무너뜨리는 구체적 시나리오여야 한다 — "경기 침체"는 안 됨.

출력은 S3에 저장하고, 입력 컨텍스트의 SHA-256을 캐시 키로 쓴다. 같은 입력이면 LLM을 다시 부르지 않는다. 재실행 폭주 방지 + 재현성.

### 품질 게이트 — DeepEval

프롬프트를 고칠 때마다 **골든 스냅샷 8건**(4종목 × bull/bear)을 재생성하고, DeepEval의 G-Eval로 3개 기준(근거 추적 가능성 / 리스크의 회사 특이성 / 스크리닝 신호 미사용)을 judge LLM이 채점한다. 비용은 1회 $0.4.

이 게이트가 실제로 잡은 사례: 9월에 Sonnet 4.6 → Sonnet 5로 모델을 바꿨더니 **24점 만점에 16점**으로 떨어졌다. judge 사유를 읽어보니 새 모델이 `key_risks` 필드에 z-score를 인용하고 있었다. 규칙 #4가 `arguments`만 가리키고 있어서 생긴 사각지대였다. 세 필드 전체로 규칙을 확장하고 자기점검 5항목을 붙였더니 24/24로 복구. 모델 교체는 프롬프트 회귀를 동반한다는 걸 숫자로 배웠다.

## 4. 3단계 — 시나리오: "옵션 C", LLM은 가격을 말하지 않는다

여기가 설계의 핵심이자 실패의 핵심이다.

처음 고민은 "LLM에게 목표가를 물을 것인가"였다. 세 가지 안을 뒀다.

- **A**: LLM이 가격 타깃을 직접 낸다 — 할루시네이션이 가격에 바로 들어간다.
- **B**: LLM 없이 Bull/Bear의 confidence를 코드로 점수화한다 — 비용 0, 학습 0.
- **C**: LLM은 **bull/base/bear 세 시나리오의 확률·근거·무효화 트리거**만 낸다. **가격은 결정적 산식**(피어 P/E × EPS, 52주 고저점)이 계산한다.

C를 골랐다. 그리고 B를 **섀도 베이스라인으로 병렬 산출**했다 — 추가 LLM 비용 0으로 "LLM 확률이 코드 점수화보다 나은가"를 12주 뒤 비교하기 위해서. 이 결정이 나중에 가장 큰 가치를 냈다.

기대수익(ER)은 `Σ p_i × (price_i / current − 1)`. 확률은 LLM, 가격은 코드. 확률과 가격을 곱하는 한 줄에서 두 세계가 만난다.

### 무효화 트리거와 자동 채점

각 시나리오에 "이 시나리오가 틀렸다고 판단할 조건"을 정량 metric으로 쓰게 했다 — `revenue_yoy < 5%`, `fcf_yoy < −20%` 같은 식. 분기 실적이 나오면 배치가 자동 채점하고, 발표 후 첫 거래일 종가를 앵커로 realized 시나리오를 분류해 **Brier score**를 누적한다. 즉 "LLM 확률이 보정돼 있는가"를 측정하는 인프라를 처음부터 깔았다.

## 5. 4·5단계 — 결정적 코드가 돈을 움직인다

**최적화**: PyPortfolioOpt mean-variance(max Sharpe). 공분산은 하이브리드 — 대각은 시나리오 분산, 비대각은 252일 역사적 상관 + shrinkage. 제약은 헌장 그대로(종목 ≤15%, 섹터 ≤35%, 최소 3%). 그리고 **현금 규칙**: 양수 ER 후보가 10개 미만이면 n/10만 투자한다. 음수 기대수익 종목을 포지션 수 채우려고 사지 않는다는 보수 원칙.

**리밸런싱**: 목표 비중과 보유의 차이를 계산해 매도 먼저, 남은 현금으로 매수. 체결가는 직전 금요일 종가(결정적, look-ahead 없음), 비용 0, 소수점 주식(MU 한 주가 계좌의 10%라 정수 주로는 비중을 못 맞춘다). **No-trade band 1.5%p** — 미세 조정은 건너뛴다. 실패하면 "보유 유지" 스냅샷만 남기고 다음 주 자연 수렴.

페이퍼 계좌는 **두 개**를 같은 규칙으로 굴렸다 — 옵션 C용과 옵션 B용. 예측 ER 비교가 아니라 **실현 수익률**로 둘을 비교하기 위해서.

## 6. 운영 — 사고 3건, 전부 설계가 아니라 배포에서

| 사고 | 원인 | 교훈 |
|---|---|---|
| 2주 결번 | zip 용량 줄이려고 pyarrow를 슬리밍했더니 전 Lambda import 즉사 | 컨테이너 배포 스크립트에 **import 스모크** 추가 |
| 3단계 결번 | `anthropic>=0.40,<2.0` 느슨한 핀 → CI가 SDK 1.x를 번들 → `temperature` 인자 제거로 40/40 실패 | 외부 SDK는 **로컬 venv와 같은 마이너 범위로 핀**. 테스트는 통과했었다 — 목 테스트는 SDK 시그니처 변화를 못 잡는다 |
| 로그 0건 (4주간) | 컨테이너 Lambda가 재사용한 IAM role의 로그 권한이 원래 함수 로그 그룹 하나에만 열려 있었음 | role 재사용 시 로그 그룹 리소스 동반 |

세 번째 결번 때 5단계는 **정상 작동**했다 — 상류가 실패하면 "목표 없음 = 보유 유지"로 스냅샷을 남기도록 설계했고, 그게 첫 실전에서 그대로 돌았다. 실패 경로를 먼저 설계한 보람이 있었다.

그리고 한 번, 검증하려고 과거 날짜로 상태 머신을 수동 실행했다가 **그 주 파티션을 현재 데이터로 덮어썼다.** S3 버저닝이 없어서 복구 불가. "과거 as_of 수동 실행 금지"를 README에 박고, 5단계는 스냅샷(불변)을 먼저 쓰고 상태(가변)를 나중에 쓰도록 순서를 고정했다.

비용: 12주 LLM 합계 **≈ $14.7**. 주 $1.05 (Bull/Bear 40콜 $0.70 + 시나리오 20콜 $0.35). 상한 $200의 7%.

## 7. 측정 — 12주 뒤 숫자가 말한 것

유효 regime(데이터 버그 수정 이후) 2026-07-14 ~ 10-19, 정기 15회 중 14회 성공, LLM 콜 840건 재시도 0.

### 7.1 확률은 상수였다

| | 값 |
|---|---|
| bull 확률 평균 / 표준편차 | 0.291 / **0.035** |
| 관측된 값 | 0.20, 0.25, 0.28, 0.30, 0.32, 0.35 — 사실상 격자 |
| Brier score (n=60) | **0.636** (합격 기준 < 0.25, 무작위 0.667) |
| 같은 입력 4회 재호출 시 bull 확률 변동 | 5종목 중 5종목 **동일값** (sd ≤ 0.024) |

모델을 Sonnet 4.6에서 5로 바꿔도, 프롬프트를 보강해도, temperature가 없는 모델에서 재호출해도 똑같았다. 흔들리는 게 아니라 **같은 숫자를 반복**했다. "세 시나리오에 확률을 매겨라"라는 과제 자체가 LLM에게서 격자 답을 끌어내는 구조라는 게 결론이다.

### 7.2 그럼 ER은 무엇이었나

확률이 상수면 ER의 변별력은 가격 산식에서만 나온다. 저장된 데이터로 뜯어보니 후보 종목의 78~92%가 `bear = base = 현재가`로 퇴화해 있었고(base·bear 가격에 "현재가 이하" cap을 둔 결과), 그 종목들의 ER은 **`p_bull × 52주고점 여력`과 소수점까지 일치**했다. 12주 동안 돌린 건 "LLM 포트폴리오"가 아니라 사실상 **"52주 고점에서 얼마나 떨어져 있나" 스크린**이었다.

여기서 1단계와 3단계가 정면충돌한다는 것도 보였다. 1단계는 모멘텀(고점 근처)을 뽑고, 3단계는 고점 아래 종목에 ER을 준다. 현재가 = 52주 고점이면 ER ≡ 0 → 탈락, 조금 내리면 편입, 반등하면 청산. 1주 왕복 매매가 6건 나왔다.

### 7.3 옵션 C vs B — 동등

| 9주 실계좌 | 옵션 C (LLM 확률) | 옵션 B (코드 점수화) | SPY |
|---|---|---|---|
| 누적 | −5.14% | −5.26% | −2.16% |
| TE (연환산) | 18.5% | 18.6% | — |

차이 0.12%p. LLM 확률은 코드 점수화보다 낫지도 못하지도 않았다 — 둘 다 정보가 없으니 당연한 결과다. SPY 대비 열위의 원인은 LLM이 아니라 **집중도**(15% cap 종목 4개)였고, 그게 헌장의 실전 전환 기준(TE ≤ 15%)을 미충족하게 만든 유일한 항목이다.

### 7.4 판정

헌장에 미리 써둔 판단 분기대로: 성공 기준 3개 중 **Brier 불합격, 트리거 적중률은 지표 정의 결함으로 판정 불가, 옵션 B 대비 동등** → "재설계 검토" 구간. 실전 전환은 **페이퍼 유지**.

## 8. 이 실험에서 LLM이 실제로 한 일

정직하게 적으면:

- **ER에 기여한 것**: 없음 (상수 확률 × 가격 = 가격).
- **기여한 것**: Bull/Bear 근거 텍스트(사람이 읽을 때 품질이 있었고 DeepEval로 측정 가능했다), 무효화 트리거(자동 채점 가능한 정량 조건을 98%의 비율로 생성했다), 그리고 **"LLM이 기여하지 않는다"는 것을 측정 가능하게 만든 구조 자체**.

세 번째가 제일 큰 수확이다. LLM 확률을 가격 산식과 분리하고, 옵션 B를 병렬로 돌리고, 모든 중간 산출물을 파티션으로 남겼기 때문에 12주 뒤에 "어디가 문제인가"를 추측이 아니라 재계산으로 답할 수 있었다. 저장된 데이터로 config 6종 × 8주를 오프라인 리플레이하는 백테스트 스크립트가 LLM 비용 0으로 돌아갔다.

---

## 9. v2에서 바꾸는 것

- **LLM을 확률 입력에서 분리** — ER 확률은 결정적(1차 균등, 이후 경험적 base rate). LLM 확률은 병렬 관찰만. LLM에게는 확률 대신 **방향 순위**(ordinal)를 묻는 실험 슬롯.
- **가격 산식**: base cap 0 → 10% (백테스트에서 퇴화 0.78 → 0.00), bull 앵커를 52주 고점에서 실적 기반 적정가로 교체 검토.
- **집중도**: 종목 cap 15% → 10% (TE 대응).
- **지표**: 트리거 적중률을 base rate 대비 lift로 재정의.
- **인프라 선행 조건**: 의존성 lockfile, SDK 메이저 이행, CI 컨테이너 자동화, S3 버저닝 — 사고 3건이 전부 여기서 났으니까.

구현은 하지 않았다. MVP 종료까지 열흘이었고, 검증할 운영 주차가 두 번뿐이었고, 12주 데이터와 단절되니까. **결정을 박제하고 코드는 다음 버전**이 헌장 2순위(명료한 의사결정 로그)에 맞는 선택이었다.

## 10. 다시 한다면

[TODO: 개인 소감. 아래는 기술적 교훈 초안.]

1. **성공 기준과 판단 분기를 먼저 쓰고, 측정 인프라를 1일차에 깔 것.** 옵션 B 병렬 산출과 트리거 자동 채점이 없었다면 12주 뒤 "느낌상 별로"밖에 못 했을 것이다.
2. **LLM에게 확률을 묻지 말 것** — 적어도 3-클래스 소프트 확률은. 격자 상수가 돌아온다. 순위·방향·근거를 묻고 확률은 데이터에서 추정하라.
3. **결정적 산식의 퇴화를 모니터링할 것.** "LLM이 문제"라고 믿기 쉬운데 실제 문제는 cap 두 개가 결합해 하방을 0으로 만든 산식이었다. 매주 "후보 중 bear=base=현재가 비율" 한 줄만 로그에 있었어도 4주 일찍 봤을 것이다.
4. **배포 파이프라인이 설계보다 먼저 무너진다.** 느슨한 의존성 핀 하나가 설계 결함 0건인 시스템을 두 번 세웠다.
5. **헌장은 쓰는 데 하루, 쓰이는 데 6개월.** 우선순위 한 줄이 수십 번의 "이거 할까?"를 끝냈다.
